# 設計の経緯

本書は規範ではない。
現行の文法と評価モデルの規範は[言語仕様](grammar.md)である。
本書には、検討の分かれ目になった判断とその理由、退けた代替案、草案間の変更を集約する。
判断の理論的な背景は[理論的背景](theory.md)が敷衍する。

## 名前の変更

前身のプロジェクトは monadic-yaml と呼ばれていた。
`>>=` や `pure` を書かせるモナディックスタイルではなく、演算を直接呼び出す Koka 風の直接スタイルを採ったことで、モナドは意味論にのみ現れて紙面には現れなくなった。
これを名前に反映し、effectful-yaml に改めた。

## 設計判断

**カーネルをただ一つの原始に絞る。**
草案 0.3 は演算 7 つとハンドラ 4 つを言語に組み込んでいたが、`$handle` と `$fn` だけではそれらを利用者が定義できず、根本的な表現能力の欠落を組み込みで塗り潰している形だった。
欠けていた能力を分解すると、任意長の構造の反復、伸長する構成（連結）、計算されたキーによるマッピング構成の三つであり、`$collect` 一つが三つとも与える。
原始に古典的な fold を選ばないのは、fold の step が「アキュムレータに一要素足す」手段すなわち連結を別途要求し、自足しないからである。
`$collect` は構成を演算の内側に持つので自足し、逆に fold は `$collect` と `$std.state` から導出できる。

**fix を置かない。**
一般再帰の原始を提供すれば、std の定義力は上がるが停止性が失われる。
std の派生ハンドラの展開に再帰は不要であり（反復はすべて `$collect` が担う）、必要なのは回数の上界つきの反復だけなので、数を構造に変える `$std.range` で足りる。
述語で止める unfold は μ 作用素として fix と同じ強さを持つため、fix と同時に棄却した。
非有界の反復（空になるまでのページネーションなど）は、1 回の評価を単位としてホスト側がループする領分である。

**演算の名前空間を開き、旧記法を廃止する。**
草案 0.3 の `$each` のようなドットなしの演算は、言語だけが演算を定義できることを意味していた。
草案 0.4 で演算名を必ずドット入りとし、標準演算を `std.` 名前空間に置くことで、標準とホスト登録が同じ機構に乗った。
予約キーは 26 個から 14 個に減り、その全てが構文と導出形になった。
旧記法の別名は残さない。二つの綴りが同じ意味を持つと、文書の検索と機械処理の両方が二重化するからである。

**欠落キーを失敗作用にする。**
草案 0.3 では存在しないキーと添字は即エラーだった。
しかしスクレイピング結果のような実データでは、キーの欠落は文書の誤りではなくデータの変動であり、既定値で埋める・その項目を捨てるという回復が本来の処理である。
そこで、文書の形の誤り（未定義の束縛、型の不一致）はエラーのまま残し、データ起因の部分性（キーと添字の欠落、未渡しのパラメータ、未初期化のセル）は `std.fail` に統一した。
maybe のような新しい作用は増やさない。失敗作用がすでに maybe の構造を持っており、その解決は `$std.opt` が担うからである（`$default` で値に埋め、`$default: {$std.where: false}` で分岐を捨てる）。
`$std.param` の `$default` も同じ機構の展開になり、遅延評価が失敗の捕捉から自然に出る。

**失敗の翻訳を `$std.opt` に一本化する。**
失敗を分岐の打ち切りに変える専用のハンドラを置く案は、その展開が `$std.opt` の `$default` を `{$std.where: false}` にした形と一致するので退けた。
同じ仕組みに入り口を二つ置くと、利用者は「失敗をどう受けるか」を語の選択として二度学ぶことになる。
undefined のような不在を表す値の導入も検討したが、打ち切りで消えるのは値ではなく分岐であり、どこまで消えるかを値では指定できない。
不在値は補間と等値比較とホスト境界のすべてで意味を決める負担も生じるので、これも退けた。
`$default: {$std.where: false}` の意図が読みにくいと分かれば、空の選択を起こす式への糖衣を後から互換に足せる。

**`pure` を置かない。**
初期スケッチでは `pure: "hello, world"` のような最小の文を検討していた。
直接スタイルでは値がそのまま計算の結果なので、`$do: ["hello, world"]` と書けば足り、専用の構文は不要である。

**モナドの選択を作用の推論に置き換える。**
「このブロックはどのモナドとして評価されるのか」という曖昧さに対して、`singleton: List` のようにブロックごとにモナドを注釈する案も考えられた。
しかし注釈は中身と乖離しうるし、注釈の異なるブロックを合成するときの統合規則が別途必要になる。
作用の推論なら、使われた演算がそのまま答えであり、合成は作用集合の合併で済む。

**`let` と `<-` を統合する。**
初期スケッチの `let:` は名前に反して bind の意味だった。
直接スタイルでは Koka の `val x = ask()` と同じく両者の区別が消えるので、`$let` 一つに統合した。
束縛が作用を起こすかどうかは、右辺に演算が見えるかどうかで判別できる。

**逐次の原始を `$let` に移し、`$do` を導出形に降格する。**
草案 0.4 の `$do` は Haskell の do 記法からの輸入だったが、直接スタイルの下で bind の含意は `$let` が担い、`$do` に固有に残った内容は値の破棄（`>>`）だけになっていた。
作用の導入は演算を置ける位置ならどこでもできるが、値を捨てて作用だけを残せるのは文の位置だけだからである。
そこで `$in` を伴う `$let` を逐次のカーネル構文とし、`$do` を `$let` への展開で定まる導出形に降格した。
Haskell の do がそれ自体 `>>=` の糖衣であることと同型になり、「リストがデータでない」例外はカーネルから消える。
表層から `$do` を削らないのは、YAML が一つのマッピング内の重複キーを許さず、捨て名の束縛の羅列が `_1` `_2` のような連番を要求するからである。
「文の羅列」を表す名前（`$steps` など）への改名も検討したが、退けた。
次項のとおり do の含意は意味論の層に残っており、名前を変える理由にならないからである。

**`let` を bind の構文とする。**
束縛と逐次を一つの構文が兼ねることは、Moggi の計算のラムダ計算（λc）に遡る。
λc は直接スタイルの `let x = e1 in e2` をモナドの意味論で bind として解釈する体系であり、本言語の `$let` はその YAML 上の再現である。
値・逐次の `$let`・それと独立な関数適用というカーネルの構成は、fine-grained call-by-value の標準形に一致する。
Koka 風の直接スタイル（紙面）と Haskell 風のモナディックスタイル（意味論）はこの解釈で結ばれ、二つの読みは同じ構文の二つの射影である（[理論的背景](theory.md)）。
したがって `$bind` のような意味論側の名前を表層に持ち込むことはしない。
名前は表層の読み（名前の定義）に与え、bind の読みは意味論が与える。

**リストの二義性を解消する。**
初期スケッチでは、末尾の `[x, y]` が「2 要素のリスト」なのか「2 つの結果を生む選択」なのか、字面から区別できなかった。
現行仕様は前者を literal なリスト、後者を `$std.each` と書き分ける。
言語仕様の用例「選択の基本形」の 18 要素版と 9 ペア版の対比がこの書き分けを示している。

**YAML タグではなく `$` キーを使う。**
`!do [f, g, h]` のようなタグ構文は YAML としては正当だが、JSON 部分集合で表現できず、タグを扱えないパーサーやツールで壊れる。
「既存の YAML (JSON) パーサーの上で動く」という前提を守るため、マッピングのキーに構文を閉じ込めた。

**`${}` の中に YAML を書けない。**
`${{$std.get: n} + 1}` のように式の中へ演算を埋め込む案は退けた。
YAML パーサーから見ればこれは一個の文字列であり、中の `$std.get` は YAML のノードにならない。
すると作用の推論も、jq やスキーマ検証のような既存ツールも、文字列の中の式言語を別途パースしなければ文書を理解できなくなり、「素の YAML」の原則が崩れる。
演算の結果を式で使うには `$let` で名前を付ける。

**関数を一引数に固定し、呼び出しを演算と同形にする。**
`$call` と名前つき引数を持つ案も考えられたが、一引数に固定すれば、関数と演算の呼び出しがどちらも `{$名前: 引数}` になり、利用側は両者を区別しなくてよい。
Koka で `ask()` と自作関数の呼び出しが同形であることに対応する。
`$fn` の引数名の列はこの固定を破らない。展開の各段が一引数の関数だからである。

**部分適用を位置のカリー化で与える。**
引数の一部を先に固定した関数値が欲しいという要求（選択子とノードを取る抽出演算の選択子だけを固定する等）に対して、三つの案を退けた。
名前指定の部分適用（マッピングで一部だけ渡すと残りを待つ形)は、適用が完了か部分かを引数の中身で判定する簿記をカーネルに要求し、展開で定義できない。
ホール記法（引数の中の穴で関数を作る形）は、穴の位置と個数と入れ子の規則が構文と推論の両方に波及する。
演算だけを関数値に変える専用形に固定引数を付ける案は、演算にしか効かず関数値に使えない。
位置のカリー化は、`$fn` の入れ子への展開だけで定まり、部分適用が通常の適用に一致し、予約キーを増やさない。
演算の部分適用は、マッピング引数を組み立てるカリー化された `$fn`（adapter）を `$let` で一度宣言する慣用で書く。

**Kleisli 合成の導出形を置かない。**
初期の草案は、演算を関数値に変える `$op` と、値を関数の列に通す `$pipe`（`$through`）を導出形として持っていた。
しかし合成の道具が独立に要るのは、作用が戻り値の型に現れるモナディックスタイルの事情である。
直接スタイルでは呼び出しの入れ子 `{$.g: {$.f: ${x}}}` がそのまま作用込みの合成になり、段が長ければ `$let` の逐次が読み下しの形を与える。
`$op` の主な用途は `$through` の段に演算を置くことだったので、`$pipe` と共に削った。
添字や計算した式の先にある関数値も、`$let` で名前に束縛してから `$.名前` で呼べば足りる。

**ホスト演算の失敗を作用にする。**
ホスト関数の例外を一律に文書のエラーとすると、セレクタの不一致のようなデータ起因の部分性を文書側で扱えず、「有れば `{value: 値}`、無ければ `{}` を返してパスアクセスに失敗させる」といった規約をホストごとに設計することになる。
専用の通知を設け、呼び出し位置の `std.fail` に翻訳することで、「データ起因の部分性は失敗作用」という既存の判断をホスト演算まで一貫させた。
通知しない例外は従来どおり捕捉できないエラーのままなので、実装の欠陥とデータの変動が混ざることはない。

**計算したキーの照会を式ではなく演算で与える。**
式のパスを `[式]` に広げる案は、最小にとどめた式文法を破り、キーの型で挙動が分かれる規則を式に持ち込むので退けた。
`$std.lookup` は選択による照合への展開で意味が定まり、欠落が `std.fail` になって既存の部分性の機構（`$std.opt`）にそのまま乗る。

**std に置く演算を構造的な役割で選ぶ。**
草案の途中までは、第一階の標準演算に `std.upper` と `std.lower` と `std.resolve` を置いていた。
しかし upper と lower があって trim や split がない線引きは説明できず、設定が求めた演算を場当たりに足す入り口になる。
そこで基準を「作用を起こす演算と、展開と停止性の設計に構造的な役割を持つ演算だけを std に置く」と定めた。
この基準で第一階に残るのは、数を構造に変える唯一の橋 `std.range` だけである。
文字列や URL のようなドメインの演算は、ホスト登録の演算（`str.upper` や `url.resolve` など）が担う。
動機となった設定はどのみち取得系のホスト演算を要求するので、ドメインの演算を std に置いてもホストなしで動く文書は増えない。

**マッピングの生成を専用構文でなくハンドラで扱う。**
計算されたキーを直接書く構文の代わりに、選択の結果を集める `$std.mapping` を置いた。
リストを集める `$std.list` と対になり、キーの条件付き省略も `$std.where` で兼ねられる。
計算されたキーの原始的な構成力は `$collect` の `$into: mapping` にあり、`$std.mapping` はその上の導出である。

**グローバル名前空間を言語に予約する。**
ローカル関数の呼び出しは `$.名前`、演算は `$名前空間.名前` と書き、ドットを含まない `$` 名前は予約キーに限る。
この三分により、言語が将来予約キーを追加しても既存の文書の意味は変わらない。
`$use` のように既定の名前空間を開いて修飾を省く案は、名前を予約済みのグローバル空間へ持ち込み、この保証を壊すので退けた。
修飾の省略は、引数を素通しする `$fn` を `$let` で短い名前に束縛する慣用で足りる。

**`std.where` を演算ではなく導出形とする。**
空の `$std.each` は分岐 0 本の選択としてすでに打ち切りを意味しており、展開 `{$std.where: 条件} ≡ {$if: 条件, $then: null, $else: {$std.each: []}}` が成立する。
これにより選択の作用に属する演算は `std.each` ただ一つになり、選択のハンドラ（`$std.list` `$std.mapping` `$std.first`）の展開から `std.where` の節が消え、作用の推論も選択を一つの名前で数えられる。
`std.where` を演算のまま残す案は、選択のハンドラごとに同型の節を一つずつ増やす費用に対して、打ち切りだけを選択と独立に差し替えたい需要を示せなかったので退けた。
打ち切りの意味を差し替えたいときは `std.each` の節で行う。
`$std.where` の表記自体は頻出の慣用なので、導出形として残す。

**`$collect` を原始演算ではなく畳み込みの構文に分類する。**
`$collect` は作用を起こさず、ハンドラで捕捉できず、補助キーを取る。この振る舞いは演算ではなく構文のものである。
名前がドットを含まない予約キーであることも、「演算の名前は必ずドットを含む」という規則も、この分類と整合する。
従来の「演算はカーネルに属さない。`$collect` はただ一つの例外」という記述は、分類の例外を仕様の言葉で塗るものだったので廃した。
展開で導出できないという性質は変わらない。一般再帰の原始を持たない言語で反復を与えるのは `$collect` だけである。

**マッピングのマージを浅いマージに限る。**
複数のマッピングを重ねる `$std.merge` の検討では、値がともにマッピングなら再帰して重ねる深いマージも候補にあった。
しかし深いマージは、値がリストのときの扱い（置き換えるか連結するか）に正解がなく、null を「キーの削除」に使う流儀は「暗黙の null を作らない」という既存の判断と衝突する。
何より構造再帰そのものを要求するので、カーネルへの展開では定義できず新しい原始になってしまう。
Nix の `//`、jsonnet の `+`、JavaScript のスプレッドのような先例も浅いマージが主流であることが支持材料になった。
そこで `$std.merge` は浅いマージに限り、入れ子を重ねたいときは利用者がその階層で明示的に `$std.merge` を書く慣用に委ねた（[std.merge](reference/std.merge.md) の例）。
後勝ちの選択は、`$let` の再束縛や `$std.set` の文書順書き込みと同じ「後が勝つ」規則に揃えたものであり、YAML 1.1 の `<<`（先勝ち）には合わせていない。
キーの位置は初出の位置を保つ。上書きのたびにキーの並びが動くと diff が不安定になるからである。
`$std.merge` は `$std.lookup` と同じく、選択と `$std.mapping`／`$std.opt` への展開で意味が定まるので、カーネルを増やさない保存的拡張である。
「第一階の標準演算は `std.range` ただ一つ」という判断（前掲）は変わらない。merge は導出できる演算であって、導出できないものと定義される第一階には属さないからである。

**自己適用を評価前の流れ検査で拒否する。**
設計原則「停止する」は草案 0.5 まで「関数値の自己適用を書かない文書」という但し書きを持ち、停止性の保証を今後の型付けに委ねていた。
草案 0.6 はこの穴を、評価前に関数値の流れを文書全体で推論し、`$fn` の間の到達の循環を拒む検査で閉じた。
実行時の燃料（適用回数や深さの上限）は退けた。上限値に根拠がなく、正当に深い有限の計算も落とし、停止性が「作用は静的に決まる」原則に反して実行時の失敗に化けるからである。
分岐の両腕に同じ型を要求する厳格な単純型も退けた。関数とデータを `$if` で分岐して `$std.list` の下で呼ぶ公認の慣用が非文法になるからである。採ったのは選択（union）を許す型に相当する流れの推論で、拒むのは自己適用が要求する循環だけである。
型注釈の構文も退けた。モナド注釈の却下（前掲）と同じく、注釈は中身と乖離しうるし、注釈の異なるブロックの合成規則を別途要求する。推論なら流れがそのまま答えであり、作用の推論と同じ出現主義に揃う。
作用の推論の追跡を「追跡不能」からエラーに変える案も退けた。追跡は `$collect` の関数の引数やハンドラの節の引数を見ない部分的な解析であり、全域にならないからである。停止性の検査は作用の推論から独立した全域の推論として置いた。

**ローカル作用名を裸の節名で宣言する。**
草案 0.6 まで、利用者が定義する作用は必ず名前空間つきの演算名（`eff.throw` など）で書かなければならなかった。
名前空間の強制は、ホスト登録の演算や将来の予約キーと衝突しないための規則であり、外の世界と約束を交わす名前には要る。
しかし一つのハンドラとその本体の中だけで完結する作用にまでこれを課すと、利用者は「レキシカルな名前の世界」と「グローバルな演算名の世界」を常に意識させられる。
`$let` が値を束縛して `$.名前` で呼ばせるのと同じことを `$with` にもさせれば、二つ目の世界は隠せる。
そこで草案 0.7 は、ドットを含まない節名をローカル作用の宣言とし、素通しの関数の束縛と、構文パスから生成した内部の演算名への脱糖で意味を定めた。
名前が宣言ごとに生成的なので、同じ `throw` を宣言する別のハンドラに偶然捕まることはない。

退けた代替案は三つある。
先頭にドットを置く節名（`.throw`）は、`return` との衝突を避けるためだけの記号であり、その一点のためにすべてのローカル宣言へ印を課す。裸の名前を許して `return` だけを孤島にするほうが、覚えることが少ない。
ドットなしの `$throw` を演算に開く案は、グローバル名前空間を言語に予約するという既存の判断（前掲）を壊し、予約キーの追加が既存文書の意味を変えうるようにする。
名前空間つきの節名の末尾区画を自動で束縛する案（`eff.throw` の節が `throw` を束縛する）は、呼び出し側の修飾しか省けず、宣言側では名前空間を書かせたままになる。名前が生成的でもないので、入れ子のハンドラが同じ末尾区画を持てば偶然の捕捉が残る。

内部名を評価時に生成する案（OCaml の作用宣言に近い形）も採らなかった。
構文パスから決めれば内部名は評価前の解析からも見えたままであり、両者の差が出るのは、素通しの閉包がハンドラの外へ脱出したうえで同じ `$handle` の別の起動の内側で呼ばれる場合だけである。
その場面はすでに誤りなので、区別のために名前の生成を評価へ持ち込む価値は薄い。

`{$.throw: 引数}` の呼び出しが普通の関数呼び出しと同じ字面になることは、設計原則「作用は紙面に現れる」との緊張を生む。
ただし `$.名前` の呼び出しはもともと本体の作用を持ちうるので（呼び出しの作用は引数と本体の合併である）、字面だけから作用の有無が読めないのは新しい事態ではない。
展開の後ではこれは演算の呼び出しそのものであり、作用の推論も従来どおり出現から作用集合を決める。
紙面に現れるのは宣言、すなわち `$with` の節名の側である。

素通しの閉包がハンドラの動的範囲の外で呼ばれることは、静的に防がず実行時のエラーとした。
静的に防ぐには閉包の脱出を追う型（Koka の named handlers のスコープ多相、Effekt の第二級のケイパビリティ）が要り、型を書く構文を持たない本言語には重すぎる。
停止性のための関数値の流れの検査が追う情報とも別物である。あちらが見るのは自己適用の循環だけだからである。

**`$.return` を予約し、即時のエラーにする。**
`$with: {return: ...}` は return 節であってローカル作用の宣言ではないので、束縛を導入しない。
したがって `$.return` はどこでも解決せず、`$let: {return: 関数}` で束縛しても呼べない。
決して成功しない形が構文上は書けてしまう状態を残すより、出現した時点で `return is reserved: $.return is not callable` と言うほうが親切である。
草案 0.6 まではこの形が動いていたので、これは破壊的変更である。
`return` に束縛すること自体と `${return}` の参照は妨げない。禁じたのは呼び出しの形だけであり、裸の識別子の空間に予約された節名が `return` ただ一つであることの帰結として説明できる。

**境界の選択を明示必須にする。**
草案 0.7 まで、どのハンドラにも捕まらずに作用境界へ達した選択は、境界が暗黙に `$std.list` として振る舞い、値がリストになっていた。
この規則は、値の形を紙面から読むために「文書のどこに選択が出現するか」の解析を読み手に要求する。
`$if` の選ばれない分岐の `$std.each` が結果を要素 1 のリストに変えるといった、実行結果からは説明できない形の決まり方も生む。
そこで草案 0.8 は、選択を値にするのはハンドラだけとし、境界へ達した選択を評価時のエラーにした。
値がリストになるのは literal なリストと選択のハンドラの値だけになり、設計原則は「作用は静的に決まる」から「形は書いたとおり」へ移った。

退けた代替案は二つある。
選択の到達を静的な出現主義の検査で捕まえる案は、関数の本体の選択を定義位置で数えることになる。
選択を含む関数を `$std.list` の下で呼ぶ公認の慣用が偽陽性になるので、検出は評価時に行う。
暗黙のリスト化を維持する案は、読み手に文書全体の出現解析を課したうえ、処理系の側でも解析が部分的（実行時のデータから選んだ関数の本体を追えない）にとどまり、追跡の切れた経路では結局実行時のエラーが残っていた。
明示のハンドラを要求すれば、形は局所に書かれ、実行時のエラーは「ハンドラを書き忘れた」という単一の理由に集約される。

この変更に伴い、実行前の作用の推論そのものを廃した。
未登録の演算の拒否は、関数値の流れの検査（0CFA）が演算のサイトごとに持つ表から行う。
こちらは出現に対して全域なので、「静的に追跡できない経路の演算は実行時にエラー」という但し書きが消えた。

## 草案 0.7 からの変更

どのハンドラにも捕まらずに作用境界へ達した選択（`std.each`）をエラーにした。境界が暗黙に全分岐をリストへ集めることはなくなり、選択を含む計算は `$std.list` `$std.mapping` `$std.first`、または `std.each` の節を持つ `$handle` で包む。
境界の既定ハンドラの系列は、失敗・パラメータ・ログ・状態の 4 段になった。
未登録の演算の評価前の拒否は、関数値の流れの検査が持つ演算のサイトの表から行うようになり、演算の出現に対して全域になった。
妥当な文書の集合が変わるため、草案を 0.8 に上げた。

## 草案 0.6 からの変更

`$handle` と `$do` の `$with` 文の節名に、ドットを含まない識別子を許した。これはローカル作用の宣言であり、素通しの関数の束縛と、構文パスから生成した内部の演算名への展開で意味が定まる。`$` で始まる節名は、将来の予約節のためにエラーのまま確保する。
レキシカルな呼び出し `$.return`（`$.return.x` を含む）を非妥当にした。`$let` で `return` に束縛することと `${return}` の参照は従来どおり妥当である。
妥当な文書の集合が変わるため、草案を 0.7 に上げた。

## 草案 0.5 からの変更

関数値の流れの検査を追加し、自己適用を含みうる文書を評価前に拒否するようにした。設計原則「停止する」の但し書きが消え、妥当な文書の評価は無条件に停止する。
閉包をホストの演算へ渡すことの禁止を、評価前の検査と実行時の検査の二重で強制した。
妥当な文書の集合が変わるため、草案を 0.6 に上げた。

## 草案 0.4 からの変更

カーネルの逐次を、`$in` を伴う `$let` に改めた。
`$do` をカーネルから外し、`$let` への展開で定まる導出形に降格した。名前と予約キーの集合は変わらない。
`$let` の評価規則が関数呼び出しの規則と同一であることを言語仕様に明記した。
値の破棄は捨て名（慣用として `_`）への束縛とし、言語は `_` を特別扱いしない。
文書を三分し、言語仕様には現行の文法だけを残して、理論的な背景を[理論的背景](theory.md)へ、設計の判断と経緯を本書へ移した。
`std.where` を作用を起こす演算から、`$if` と空の `$std.each` への展開で定まる導出形に改めた。選択の作用に属する演算は `std.each` ただ一つになった。
`$collect` の分類を「唯一の原始演算」から畳み込みのカーネル構文に改めた。カーネルの 6 形の列挙は変わらない。

## 今後の課題

- スキーマによるデータの型付け（文書の形の宣言と検証）。停止性の保証は草案 0.6 の関数値の流れの検査で先行して達成した。
- パラメータを持つハンドラの糖衣構文。`$std.state` の展開が示す「節が関数を返す」形を直接書ける構文。
- 関数値をデータとして直列化する形式。
- 複数文書のストリームの扱い。
- マッピングのキー順序の保存をパーサーに要求することの明文化。
- `$let` の `$where` 補助キー（内包表記の糖衣）。`$do` と `$std.where` の使用感を見て判断する。
- 式のパスの計算キー（添字位置の束縛名）と `$std.lookup` の統廃合。
