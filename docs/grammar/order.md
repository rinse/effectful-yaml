# キーの順序

YAML の表現モデルでは、マッピングのキーは順序を持たない[^1]。
effectful-yaml は、キーの並びを一部の位置で評価の順序やデータの並びとして読む。
処理系は、キーを文書順に保つパーサーで文書を読まなければならない。
それ以外の位置では、キーを並べ替えても文書の意味は変わらない。

[^1]: YAML 1.2 はマッピングのキーの並びを直列化の細部とし、表現グラフを組み立てるときに使うべきではないとする。

## 並びが意味を持たない位置

`$` 式の形は、マッピングがどの種類のキーを持つかで判定し、頭キーどうしの並びを除いてキーの位置を見ない（[`$` 式の形](reading.md)）。
したがって、次のキーはどの位置に書いても意味が同じである。

- 主形の主キーと補助キー（`$if` と `$then` と `$else`、`$fn` と `$body`）。
- `$in` とデータのキーの、頭キーに対する位置。頭は、書いた位置によらず残り全体を本体に取る。データのキーどうしの並びは、後述の「データのマッピングの値」のとおり意味を持つ。
- `$default`。形の判定は `$default` を除いてから行う。
- `$handler` の節のマッピングの中の節。ただし、二つの節が同じ演算に解決する場合は後述の「並びの意味が未定義の場合」にあたる。

```yaml
$in:
  $else: small
  $if: ${x > 1}
  $then: large
$let:
  x: 2
```

```yaml
large
```

## 並びが意味を持つ位置

### $let の束縛

`$let` は右辺を文書順に評価し、後の右辺から先の束縛だけを参照できる（[$let](syntax.md)）。
このため束縛の並びは、スコープと作用の順序を決める。

- **スコープ**：`{$let: {y: "${x}", x: 1}, $in: "${y}"}` は、`y` の右辺から `x` が見えないので、評価前に `undefined reference` で拒まれる。
- **作用の順序**：右辺の作用は書いた順に起きる。`std.each` より前に書いた右辺は選択の前に一度だけ評価され、後に書いた右辺は分岐ごとに評価される。

```yaml
$handler: {$std.state: {n: 0}}
$in:
  $handler: ${std.list}
  $let:
    a: {$std.get: n}
    x: {$std.each: [1, 2]}
    _: {$std.set: {n: "${x}"}}
  $in: ${a}
```

```yaml
[0, 0]
```

`a` は選択の前に一度だけ読まれるので、両方の分岐が `0` を見る。
`a` と `x` を入れ替えると `a` は分岐ごとに読まれ、状態のハンドラが選択のハンドラより外側にあるので、2 本目の分岐は 1 本目が書いた `1` を見る。
値は `[0, 1]` になる。

### $for の束縛

`$for` は `$let` に展開されるので（[$for](derived.md)）、`$let` の束縛の並びが決めることをそのまま決める。
加えて、先に書いた束縛が外側の選択になるので、束縛の並びは分岐の並びを決める。

```yaml
$handler: ${std.list}
$for:
  i: [1, 2]
  j: [a, b]
$in: ${i}${j}
```

```yaml
[1a, 1b, 2a, 2b]
```

`i` と `j` を入れ替えると `j` が外側の選択になり、値は `[1a, 2a, 1b, 2b]` になる。

### 頭キーどうしの並び

一つのマッピングに頭キー（`$let`、`$for`、`$handler`）を並べると、先に書いた頭が外側になる（[`$` 式の形](reading.md)）。
後に書いた頭は先に書いた頭の本体の中にあるので、頭キーの並びは次の二つを決める。

- **ハンドラの範囲**：`$handler` が処理するのは、後に書いた頭と残りの本体が起こす作用だけである。
- **スコープ**：先に書いた頭が導入した束縛（ローカル作用の宣言を含む）は、後に書いた頭の式（`$let` と `$for` の右辺、`$handler` の式）から見える。逆向きには見えない。

```yaml
$handler: ${std.list}
$for:
  i: [1, 2]
v: ${i}
```

```yaml
- v: 1
- v: 2
```

`$for` を先に書くと、選択が `std.list` の外で起きて境界へ達するので、`unhandled choice` のエラーになる。

### データのマッピングの値

`$` キーを持たないマッピングは、値を文書順に評価する（[評価の規則](reading.md)）。
呼び出しの引数に書いたマッピング（`$std.set` の複数のセル、`$std.lookup` の `in` と `key` など）も、この規則で評価される。
値の並びが何を決めるかは、値どうしが同じ作用境界の中にあるかどうかで異なる。

同じ境界の中では、値の作用が文書順に周囲の計算へ合流する（[合成・部分処理・境界](effects.md)）。
状態の読み書きは書いた順に起きる。

```yaml
$handler: {$std.state: {n: 0}}
a: {$std.set: {n: 1}}
b: {$std.get: n}
```

```yaml
a: null
b: 1
```

`a` と `b` を入れ替えると、`b` の読み出しが書き込みより先に起きるので、`b` は `0` になる。

選択では、先に書いたキーが外側の選択になる。

```yaml
$handler: ${std.list}
a: {$std.each: [1, 2]}
b: {$std.each: [x, y]}
```

```yaml
- {a: 1, b: x}
- {a: 1, b: y}
- {a: 2, b: x}
- {a: 2, b: y}
```

`a` と `b` を入れ替えると `b` が外側の選択になり、`b: x` の二つの分岐が先に並ぶ。

一方、兄弟関係にある二つの境界は作用を共有しないので、値は並びに依存しない（[作用境界](effects.md)）。
それでも評価は文書順に進むので、処理系の外から観測できる振る舞い（ログの出力順、ホストの演算を呼ぶ順、最初に報告される失敗）は並びに従う。

```yaml
a: {$std.fail: A}
b: {$std.fail: B}
```

`a` が先に評価されるので、文書全体は `A` の失敗でエラーになる。
キーを入れ替えると `B` の失敗でエラーになる。

### データとしてのキーの並び

マッピングをデータとして受け取る演算と関数は、エントリを文書順に扱う。

- `std.each` はマッピングのエントリを文書順に選ぶ。選択を処理するハンドラはこの順に従うので、`std.list` の要素と `std.mapping` のキーはこの順に並び、`std.first` は文書順で最初に成功したエントリを採る。
- `std.collect` はマッピングのエントリを文書順に回る。
- `std.merge` は、各キーを最初に現れた位置に置く。

評価したマッピングも、キーを文書順のまま保つ。
文脈の導入を伴うマッピングでは、頭キーを除いた残りのキーがこの順に並ぶ。

```yaml
$handler: ${std.first}
$for:
  e: {b: 2, a: 1}
$in: ${e.key}
```

```yaml
b
```

どちらのエントリも失敗しないので、文書順で最初の `b` が採られる。

## 並びの意味が未定義の場合

`$handler` の節のマッピングで二つの節が同じ演算に解決するとき、どちらの節がその演算を処理するかは未定義である。

```yaml
$let:
  e: ${std.each}
$handler:
  std.each: {$fn: _, $body: first}
  .e: {$fn: _, $body: second}
$in: {$std.each: [1]}
```

節の名前 `std.each` と `.e` は綴りが異なるので YAML の重複キーの禁止には当たらず、どちらも同じ演算 `std.each` に解決する。
文書はこの場合の値に頼るわけにはいかない。
