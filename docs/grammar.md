# effectful-yaml 言語仕様（草案 0.1）

effectful-yaml は、素の YAML の上に効果つき計算を埋め込む言語である。
すべての文書は一般の YAML パーサーでそのままパースでき、`$` で始まるキーを持つマッピングだけが計算として解釈される。
`$` を含まない YAML 文書は、それ自身を値とする妥当なプログラムである。

本仕様は名前として monadic-yaml ではなく effectful-yaml を採る。
後述するとおり、この言語は `>>=` や `pure` を書かせるモナディックスタイルではなく、演算を直接呼び出す Koka 風の直接スタイルを採用しており、モナドは意味論にのみ現れて紙面には現れないからである。

## 設計原則

- **素の YAML**：文法上の拡張を一切持たない。特殊な構文はすべてマッピングのキーと文字列の中に閉じ込める。YAML タグ（`!do` など）を使わないのは、タグが JSON 部分集合で表現できず、タグを拒否するパーサー[^1]や jq のような既存ツールと相性が悪いからである。
- **効果は紙面に現れる**：効果を起こすのは演算（`$each` や `$get` のような `$` キー）だけである。参照 `${x}` は純粋であり、効果を隠さない。
- **効果は静的に決まる**：ブロックの効果は、演算が構文上どこに出現するかだけで決まり、実行時の分岐に依存しない。評価結果の形（単値かリストか）も効果から決まる。
- **リストは常にデータ**：YAML のリストがデータでなくなるのは `$do` の直下だけである。この例外を一つに絞ることで、「このリストは値なのか文の並びなのか」という読み手の迷いをなくす。
- **暗黙の null を作らない**：未定義の参照、渡されていないパラメータ、未初期化のセルの読み出しは、null になるのではなくエラーになる。

[^1]: たとえば PyYAML の `safe_load` は、登録されていないローカルタグを既定で拒否する。

## 評価モデル

文書はテンプレートとして外側から評価される。
評価関数は次の規則に従う。

- スカラーは、`${...}` の補間を解決した値になる。
- リストは、各要素を先頭から順に評価したリストになる。
- `$` キーを持たないマッピングは、各値を文書順に評価したマッピングになる。
- `$` キーを持つマッピングを**フォーム**と呼び、キーごとに定められた規則で評価する。

一つのマッピングに置ける主キー（`$do` や `$each` など）は一つだけである。
`$then` のような補助キーは、主キーに従属するものだけを置ける。
`$` キーとそれ以外のキーの混在はエラーである。

### 効果境界

データの中に現れた最も外側のフォームを**効果境界**と呼ぶ。
境界の内側で演算が起こす効果は、途中にハンドラフォームがなければ境界まで伝播し、そこで処理系の**既定ハンドラ**が処理する。
入れ子のフォームは境界にならないので、`$do` の中の `$do` は Haskell の do 式の入れ子と同じく、単なるグループ化である。

演算はフォームの引数の中であればどこにでも置ける。
たとえば文 `- [1, {$each: [a, b]}]` はリストの要素の位置で選択を行うので、外側のブロック全体が 2 通りに分岐する。

境界が互いに独立であることには意味がある。
兄弟関係にある二つの境界は効果を共有しないので、データ部分の評価は順序に依存しない。
複数の場所で状態や選択を共有したければ、その範囲全体を一つの `$do` で包み、単一の境界にする。

### 効果の推論

各ノードの**効果集合**は、その内側に出現する演算の効果を合併し、ハンドラフォームが処理する効果を除いたものである。
出現だけを見るので、実行されない分岐の演算も効果に数える。
これにより評価結果の形が実行前に定まる。

- 効果集合に**選択**（`$each` と `$where`）が残っている境界は、全分岐の結果を文書順に並べたリストに評価される。
- それ以外の境界は単値に評価される。

既定ハンドラは外側から fail、reader、log、state、選択の順に重なる。
state が選択より外側にあるため、状態は分岐をまたいで文書順に貫流する。
分岐ごとに独立した状態が欲しい場合のための明示的な state ハンドラは今後の課題とする。

## 参照と式

**参照**：`${式}` は文字列の中に式の値を埋め込む。
文字列全体が一つの `${式}` であるときは値そのもの（型を問わない）になり、それ以外のときは値を文字列化して埋め込む。
リストとマッピングと null の文字列化はエラーである。

参照が解決するのは `$let` が導入した束縛だけである。
パラメータは `$param`、状態は `$get` という演算を通じて読む。
この区別により、効果を起こす読み出しは必ず演算として紙面に現れる。

YAML の規則上、`[...]` や `{...}` のフロー形式の中では `${x}` を含むスカラーに引用符が必要になる[^2]。
ブロック形式ではそのまま書ける。
本仕様の用例は、参照を含む箇所をブロック形式で書くことでこれを避けている。

[^2]: フロー文脈のプレーンスカラーは `{` などのフロー指示子を含められない（YAML 1.2 の ns-plain-safe(flow)）。これは本言語ではなく YAML 自体の制約である。

**エスケープ**：文字列とキーの中の `$$` は literal な `$` 一文字になる。
たとえば値 `"costs $$5"` は `costs $5` に、キー `$$do` は literal なキー `$do` に評価される。

式の文法は次のとおり最小限にとどめる。

```
式      := 論理和
論理和  := 論理積 ("||" 論理積)*
論理積  := 否定 ("&&" 否定)*
否定    := "!" 否定 | 比較
比較    := 加算 (("==" | "!=" | "<" | "<=" | ">" | ">=") 加算)?
加算    := 乗算 (("+" | "-") 乗算)*
乗算    := 単項 (("*" | "/" | "%") 単項)*
単項    := 数値 | '文字列' | true | false | null | 参照名 | "(" 式 ")"
参照名  := 名前 ("." 名前 | "[" 自然数 "]")*
```

- 比較 `==` と `!=` は値の構造的な等価性を判定する。大小比較と算術は数値だけに定義され、それ以外の型に適用するとエラーになる。
- `&&` と `||` と `!` の被演算子、および `$if` と `$where` の条件は真偽値でなければならない。真偽値への暗黙の変換は行わない。
- `.名前` はマッピングのキーを、`[自然数]` はリストの 0 起点の添字を参照する。存在しないキーや添字はエラーになる。
- 0 除算はエラーになる。文字列の連結は補間で書く。

## 特殊フォーム

特殊フォームは効果を持たない構文であり、`$do` と `$let` と `$if` の三つだけである。

### $do

```yaml
$do:
- 文1
- 文2
- 結果式
```

`$do` は直下のリストを文の並びとして先頭から評価し、最後の文の値をブロックの値とする。
これが「リストはデータ」の唯一の例外である。
空の `$do` の値は null である。

文には任意の式のほか、`$let` と後述の演算を置く。
`$let` と `$where` と `$set` と `$log` は文としては null に評価されるので、ブロックの結果にしたい値は最後の文に書く。

### $let

```yaml
- $let:
    x: 式1
    y: 式2
```

`$let` は `$do` の文としてだけ書ける。
右辺を文書順に評価し、その値を名前に束縛して、ブロックの残りの文から `${x}` で参照できるようにする。
後の束縛の右辺からは先の束縛を参照できる。
同じ名前の再束縛は許され、外側の束縛を隠す。

右辺の評価は効果を起こしてよい。
`x: {$each: [a, b, c]}` は「a、b、c のそれぞれを x として」と読め、Haskell の `x <- ...` に相当する。
束縛が効果を起こすかどうかは、右辺に演算が見えるかどうかと一致する。

### $if

```yaml
$if: 条件式
$then: 式
$else: 式
```

`$if` は条件の値に応じて `$then` か `$else` の一方だけを評価する。
`$else` は省略できない。
条件が真偽値でなければエラーになる。

## 標準演算

演算は効果を起こすフォームである。
各演算は一つの効果に属し、その効果は境界の既定ハンドラか明示のハンドラフォームが処理する。

| 演算 | 効果 | 意味 |
|---|---|---|
| `$each: リスト` | 選択 | リストの各要素を一つずつ選ぶ。値は選ばれた要素。 |
| `$where: 条件式` | 選択 | 条件が偽の分岐を打ち切る。 |
| `$param: 名前` | reader | 起動時に与えられたパラメータを読む。 |
| `$get: 名前` | state | セルの現在値を読む。 |
| `$set: マッピング` | state | セルに値を書く。未作成のセルは作られる。 |
| `$log: 式` | log | 値を処理系のログ出力に流す。 |
| `$fail: 式` | fail | 計算を失敗させる。値をエラーメッセージとする。 |

補足を述べる。

- `$each` の引数は評価の結果がリストでなければならない。`$each: ${xs}` のようにデータ駆動の反復が書ける。空リストは分岐 0 本を意味し、`$where: false` と同じく打ち切りになる。
- `$param` は補助キー `$default` を取れる。パラメータが渡されていないとき、`$default` があればその値、なければエラーになる。
- `$get` の名前空間は `$let` の束縛とは別である。同名でも互いに関係しない。
- `$set` は複数のセルを文書順に書ける。値は null である。

## ハンドラフォーム

ハンドラフォームは、内側のブロックの効果をその場で処理し、外へ伝播させないフォームである。
草案 0.1 では次の二つを定める。

- **`$all: 式`**：選択を処理し、全分岐の結果を文書順に並べたリストに評価される。内側に選択がなければ要素 1 のリストになる。分岐の中の fail は処理せず、全体の失敗として伝播させる。
- **`$first: 式`**：選択と fail を処理し、失敗しなかった最初の分岐の値に評価される。すべての分岐が失敗または打ち切りなら、全体が fail になる。

利用者が独自のハンドラを YAML の中で定義する構文（継続 `$resume` を含む）は今後の課題とし、当面のハンドラは処理系への登録によって増やす。

## 利用者定義の効果

予約されていない `$` キーは、すべて利用者定義の演算の呼び出しである。

```yaml
password: {$vault.read: secret/db/password}
```

引数は評価されてから、処理系に登録されたハンドラに渡され、ハンドラの返す値が演算の値になる。
名前の衝突を避けるため、`$vault.read` のようにドットで名前空間を切ることを推奨する。

効果の推論は利用者定義の演算にも及ぶ。
文書に出現する演算を集めれば、その文書が要求するハンドラの一覧、すなわち文書の**効果シグネチャ**が評価前に得られる。
処理系は、ハンドラの登録されていない演算を含む文書を評価前に拒否する。

予約キーは次の 15 個である。
`$do` `$let` `$if` `$then` `$else` `$each` `$where` `$param` `$default` `$get` `$set` `$log` `$fail` `$all` `$first`

## 用例

### 値だけの文書

```yaml
greeting: hello
```

フォームを含まない文書はそれ自身に評価される。
`pure` に相当する構文が要らないのはこのためで、値はそのまま計算の結果である。

### 選択の基本形

```yaml
$do:
- $let:
    x: {$each: [a, b, c]}
    y: {$each: [x, y, z]}
- $each:
  - ${x}
  - ${y}
```

効果集合は選択だけなので、境界の値は全分岐の結果のリストになる。
最後の文も選択なので、分岐は 3 × 3 × 2 の 18 本ある。

```yaml
[a, x, a, y, a, z, b, x, b, y, b, z, c, x, c, y, c, z]
```

最後の文を literal なリストに変えると、意味が「2 つの結果を選ぶ」から「2 要素のリストを返す」に変わる。

```yaml
$do:
- $let:
    x: {$each: [a, b, c]}
    y: {$each: [x, y, z]}
- - ${x}
  - ${y}
```

```yaml
[[a, x], [a, y], [a, z], [b, x], [b, y], [b, z], [c, x], [c, y], [c, z]]
```

この 2 例の対比が「リストは常にデータ、選択は `$each`」という原則の眼目である。

### 打ち切りつきの選択

```yaml
$do:
- $let:
    x: {$each: [1, 2, 3]}
    y: {$each: [1, 2, 3]}
- $where: ${x < y}
- - ${x}
  - ${y}
```

```yaml
[[1, 2], [1, 3], [2, 3]]
```

リスト内包表記に相当する形である。

### パラメータと条件分岐

```yaml
server:
  host: {$param: db_host}
  port: {$param: db_port, $default: 5432}
  tls:
    $if: {$param: use_tls}
    $then:
      cert: /etc/ssl/cert.pem
    $else: null
```

`db_host: example.com` と `use_tls: false` を渡して評価すると次になる。

```yaml
server:
  host: example.com
  port: 5432
  tls: null
```

三つのフォームはそれぞれ独立の境界であり、reader は読み出し専用なので、評価順序は結果に影響しない。

### 分岐を貫く状態

```yaml
$do:
- $set: {n: 0}
- $let:
    name: {$each: [web, db, cache]}
    c: {$get: n}
- $set:
    n: ${c + 1}
- name: ${name}
  id: ${c}
```

state の既定ハンドラは選択より外側にあるので、セル `n` は分岐をまたいで貫流し、連番が振られる。

```yaml
- name: web
  id: 0
- name: db
  id: 1
- name: cache
  id: 2
```

### 最初に成功する分岐

```yaml
log_level:
  $first:
    $do:
    - $let:
        v: {$each: [{$param: log_level, $default: null}, {$param: fallback_log_level, $default: null}, info]}
    - $where: ${v != null}
    - ${v}
```

`$first` が選択を処理するので、この境界の値はリストではなく、条件を満たした最初の分岐の単値になる。
パラメータが一つも渡されていなければ `info` になる。

## 設計判断

本節では、初期スケッチから変更した点とその理由を記す。

**`pure` を置かない。**
スケッチでは `pure: "hello, world"` のような最小の文を検討していた。
直接スタイルでは値がそのまま計算の結果なので、`$do: ["hello, world"]` と書けば足り、専用の構文は不要である。

**モナドの選択を効果の推論に置き換える。**
「このブロックはどのモナドとして評価されるのか」という曖昧さに対して、`singleton: List` のようにブロックごとにモナドを注釈する案も考えられた。
しかし注釈は中身と乖離しうるし、注釈の異なるブロックを合成するときの統合規則が別途必要になる。
効果の推論なら、使われた演算がそのまま答えであり、合成は効果集合の合併で済む。

**`let` と `<-` を統合する。**
スケッチの `let:` は名前に反して bind の意味だった。
直接スタイルでは Koka の `val x = ask()` と同じく両者の区別が消えるので、`$let` 一つに統合した。
束縛が効果を起こすかどうかは、右辺に演算が見えるかどうかで判別できる。

**リストの二義性を解消する。**
スケッチでは、末尾の `[x, y]` が「2 要素のリスト」なのか「2 つの結果を生む選択」なのか、字面から区別できなかった。
本仕様は前者を literal なリスト、後者を `$each` と書き分ける。
用例の 18 要素版と 9 ペア版の対比がこの書き分けを示している。

**YAML タグではなく `$` キーを使う。**
`!do [f, g, h]` のようなタグ構文は YAML としては正当だが、JSON 部分集合で表現できず、タグを扱えないパーサーやツールで壊れる。
「既存の YAML (JSON) パーサーの上で動く」という前提を守るため、マッピングのキーに構文を閉じ込めた。

## Haskell との対応

用例「選択の基本形」は次の do 式に対応する。

```haskell
do x <- each ["a", "b", "c"]
   y <- each ["x", "y", "z"]
   each [x, y]
```

束縛を持たない文の並び `$do: [f, g, h]` は `f >> g >> h`、すなわち `f >>= \_ -> g >>= \_ -> h` に対応する。
意味論のレベルでは、`$do` の文の並びは効果のモナドにおける `>>=` の連鎖に脱糖され、既定ハンドラとハンドラフォームがそのモナドの解釈を与える。

## 今後の課題

- 関数の定義と適用（`$fn` と `$call`）、およびそれによる Kleisli 合成の表現。
- YAML 内でのハンドラ定義（継続 `$resume` を含む）。
- 分岐ごとに独立した状態を与える明示的な state ハンドラ。
- `$each` のマッピングへの拡張と、計算されたキーによるマッピングの生成。
- マッピングのキーの条件付き省略（null を入れることと、キーがないことの区別）。
- 文字列関数などの式言語の拡張。
- スキーマによる型付けと、効果シグネチャの文書内宣言。
- マッピングのキー順序の保存をパーサーに要求することの明文化。
